High-Level System Design

Agentic EDA Demo

Stock tweets + daily prices in, a checked exploratory analysis out. One idea decides every boundary in this design: code computes and judges; the model chooses and explains.

1Requirements

An offline-friendly, single-machine pipeline that turns an arbitrary tweets + prices pair into an honest report — and that can prove where every number came from.

DriverWhat it forces in the design
Trustworthy numbersEvery figure in prose must trace to a computation with an id. A verification stage sits between generation and publication.
Corpus is dirty and cross-postedAttention is measured on ticker-specific text, not row counts. Coverage tiers exist because five tickers are 100% reposted.
Claims must not be over-readTesting, multiplicity correction and holdout replication are enforced by code, never requested from a model.
Must run with no API keyThe whole analysis path is deterministic; the model is an optional overlay with a templated fallback at every seam.
Cheap to re-runThe expensive stage (feature panel) is cached behind a config-and-input fingerprint.
Analyst changes, not code changesWindows, thresholds, dataset choice, even column names live in two YAML files.
Non-goals

Not a trading system, not a backtest, no execution or position sizing, no web UI, no distributed compute, no streaming. Single process, single machine, batch runs.

2The mental model

Three planes, and the separation between them is the architecture:

  1. The deterministic plane — ingestion, cleaning, features, statistics, status assignment. Pure functions over a table. Reproducible, unit-tested, no network.
  2. The orchestration plane — one coordinator that sequences stages, owns the tool budget, decides when the holdout is read, and writes the manifest. Deliberately not an LLM.
  3. The model plane — three narrow LLM roles: propose a vocabulary, pick follow-up questions, write prose. Every one of them can degrade to a deterministic fallback without failing the run.

An agent never scores a row, never sees the full dataset, never chooses which period to read, and never decides whether a result is "supported". Those four prohibitions explain almost every interface below.

The single outbound door. 4.4 Analysis plane — deterministic, the source of every number

C11

Tool registry & typed tools

deterministic

Fourteen pure analyses — coverage, distributions, time series, text stats, sample tweets, correlation, bucketed forward returns, correlation matrix, spike days, attention vs price, holdout check, p-value adjustment — each with a pydantic parameter schema and a uniform ToolResult (stats, table, chart, caveats, n_units, result_id). The catalog is a fixed list, so a model cannot extend what can be called. The registry is rebuilt per run so one run's results can never be cited as another's evidence.

Interface
registry.call(tool, params, period)
Depends on
panel, tweets, tiers, settings, C12 inference
Used by

Fails by
ToolError → recorded, never fatal
C12

Inference kernel

deterministic

Five small statistics with one opinion baked in: because a single news day is counted many times, the resampling unit is the session block, not the row. Provides Spearman with p-value, block bootstrap confidence intervals, a bootstrap p-value for bucket spreads, Benjamini–Hochberg q-values, and a robust median/MAD z-score for attention spikes.

Interface
spearman · block_bootstrap · benjamini_hochberg · robust_z
Depends on
numpy, scipy, bootstrap config
Used by
C11 tools
Fails by

C16

Findings, status rules & claim checker

deterministic

A pure function turns tested numbers into exactly four statuses — observed, supported, not_replicated, inconclusive — with two structural overrides: a tier-C ticker can never exceed observed, and a tier-B per-ticker claim is capped unless its text was restricted to own text. The claim checker then scans the prose for numbers and rejects any that does not match a value in a cited tool result.

5Request lifecycle

What happens on run.py --dataset full run, in order. The steps that can involve a model are marked.

  1. Configure. YAML + .env resolve into Settings; the CLI flag overrides the active dataset for this run only.
  2. Resolve the vocabulary. If an induced lexicon is already frozen, use it and skip induction — re-inducing every run would make numbers depend on a fresh, meaningless model call.
  3. Induce model (only if needed and a key exists). Sample strata → model proposes terms → deterministic gate accepts/rejects each → freeze and write an active pointer.
  4. Build or load the panel. Cache fingerprint matches → load; otherwise clean, align, score, aggregate, save.
  5. Build the registry. One per run, carrying that run's panel, tiers and data version.
  6. Run the playbook. 14 fixed calls; failures are recorded, not raised.
  7. Explore model (full mode). The agent sees a trimmed digest plus discovery-period access, and issues ≤12 tool calls. Every call returns a stored ToolResult.
  8. Verify. The coordinator re-runs each tested discovery result on the holdout (capped at 8) and applies Benjamini–Hochberg across all tests.
  9. Judge. Status rules assign one of four statuses; tier overrides applied. No model is consulted.
  10. Write prose model (full mode). The presenter drafts the narrative citing result ids; the claim checker then verifies every number against its cited result.
  11. Publish. Report, findings, results, manifest and figures are written to the run directory; the terminal shows the summary and the chart menu.
Why this shape

Steps 8 and 9 sit between generation and publication. That ordering is the whole safety story: a claim cannot reach the reader without passing through code that knows the ground truth.

6Data & storage model

Two things are stored: an immutable tree of inputs and config that everything is keyed to, and an append-only collection of run directories. Stages communicate through files and typed objects, never by mutating each other's state.

The one key worth understanding: data_version

A hash over the input file digests, both config files, the lexicon id and the code version. It appears in every tool result's caveats and in the manifest. Two consequences: a cache hit is trustworthy rather than merely convenient, and any metric change can be attributed to a specific change in data or configuration.

7Dependencies

7.1 Component dependency rules

Layering is enforced by direction of imports. Four rules carry most of the weight:

  1. Analysis never depends on the model plane. Every tool is a pure function of the panel and validated parameters; that is exactly why the playbook can run with no endpoint and why a holdout re-run is possible at all — the same call with the same parameters, one period over.
  2. The model plane depends on analysis, never the reverse. Agents call tools; tools have no reference to agents. The catalog is a fixed list, so the callable surface cannot grow at runtime.
  3. The coordinator is a composition root. Data flows down, decisions flow up. No stage sequences another stage.
  4. Configuration and the inference kernel are leaves. They are imported widely and import nothing from the pipeline.

8Invariants & trust boundaries

The interesting part of this design is not what it computes — it is what it refuses to let a model do.

BoundaryHow it is enforced, not merely requested
The model never computes a numberIts only write path is a tool call, and a tool returns a stored ToolResult. Prose numbers are re-verified against those results before publication.
The model never sees the full datasetIt receives a trimmed digest and, at most, a bounded stratified sample of text.
The model cannot peek at the holdoutThe explorer's tool calls are constrained to the discovery period in code; the holdout is reachable only through a coordinator-triggered re-run.
The model cannot decide "supported"Status is a pure function of q-value, confidence interval, holdout sign and coverage tier.
A claim cannot outrun its evidenceEvery finding must cite a result id; the claim checker strips or flags any number that fails to match.
Every result is attributableresult_id + data_version + manifest, written for each run.
The cache cannot lieThe fingerprint covers inputs, both config files, the lexicon id and the code version; a mismatch forces a rebuild.
Inputs are never modifiedAll reading is read-only; the ZIP is never extracted onto disk.

11Extension points

To do thisTouch exactly this
Add a new analysisWrite a function with a pydantic params class in the appropriate tool module and register it; the agent can now call it, and the playbook gains one list entry.
Add a new datasetOne entry under datasets.sources, plus a column map if the headers differ.
Change the vocabularyRe-run induce; the gate decides what is frozen. Or ship a new default lexicon and point sentiment.lexicon at it.
Tighten the statisticsexperiments.yaml only — block size, resamples, alpha.
Add a model providerNothing, if it speaks OpenAI-compatible HTTP. Otherwise the gateway is a single class.
Change what a run outputsThe reporting layer — it is a pure view over RunState.

12Known limits

  • One regime. A single year that includes the 2022 drawdown. Nothing generalises past that window.
  • The unit is the ticker-day, not the tweet. Overlapping forward returns are handled with session-block resampling, but the effective sample stays small.
  • Cross-posted text is structural. Tier C tickers can never yield more than an observed finding, by rule.
  • Sentiment is scored by general-purpose tools (a lexicon blended with VADER) that are weak on finance slang and sarcasm.
  • Agent choices are not reproducible, even at temperature 0. The deterministic layer is; the questions an agent asks may differ between runs.
  • The holdout is 30% of one regime, so replication is weak evidence, and the report's wording says so.
  • Single-machine, batch, in-memory. The design optimises for auditability, not throughput.
The one-sentence summary

A deterministic analysis engine with a cache-keyed data plane and a strict evidence contract, wrapped by an optional model plane whose only powers are choosing questions and writing prose — both of which are checked by code before a reader ever sees them.
